# inari-server — Agent Guide

Control plane for Inari: REST API/BFF, agent gRPC gateway, tenancy & identity, cluster registry, catalog service, orchestrator, cloud accounts, resources inventory, audit, approvals, notifications, extension host, fleet manager, policy service, tenant zone factory (plan §5.2).

Stack: Go, PostgreSQL, chi/Huma (REST/OpenAPI codegen), gRPC (agent gateway), NATS (event bus), OpenFGA (authz)

## Key architecture constraints
- **Modular monolith**: one deployable binary; every module (Tenancy, Cluster Registry, Agent Gateway, Catalog, Orchestrator, Cloud Accounts, Resources Inventory, Audit, Approvals, Notifications, Extension Host, Fleet Manager, Policy Service, Tenant Zone Factory, Scaffolding/Software Templates) behind a strict internal interface so it can be extracted later (§5.2).
- The Orchestrator's git backend is resolved **per tenant** via `gitprovider.Resolver` (ADR-0010 hybrid model): a tenant git-config with `githubApp` (BYO app credential *reference* — appId + installationId + optional GHE `apiBase` + ESO secret ref; keys never in the DB, loaded from `INARI_TENANT_GIT_KEY_MOUNT_ROOT` mounts by `internal/tenancy/gitkeys`) wins; otherwise the platform app (`INARI_GITHUB_APP_ID` + `INARI_GITHUB_APP_PRIVATE_KEY_FILE`, optional GHE `INARI_GITHUB_API_BASE`) resolves its installation for the state-repo org at runtime (`GET /app/installations`, TTL cache, 401/404 invalidation). `INARI_GITHUB_APP_INSTALLATION_ID` is deprecated (cache seed only). Scaffold/TZF address platform-owned repos through `gitprovider.PerRepo` (platform app only). Deploy failures surface 412 (app not installed, with install link) / 502 (credentials revoked); `GET git-config` returns a cached `gitProviderStatus` probe. Omitting `githubApp` on PUT git-config preserves the stored reference (TZF-safe); `clearGithubApp: true` explicitly removes it (revert to model A).
- The Scaffolding module (`internal/scaffold`) exposes two REST surfaces over the same service: the canonical API (`POST /tenants/{org}/templates/{name}/runs`, `GET/POST /tenants/{org}/scaffold-runs/{runId}[/cancel][/retry]`) and a UI-compat adapter (`POST/GET /tenants/{org}/scaffolds[/{runId}]`) whose JSON shapes are pinned to the hand-written inari-ui wizard client (`inari-ui/src/api/templates.ts`) — change that client contract only server-side. Template ingestion goes through the `TemplateSource` seam: `FilePuller` (local dir, dev/baked-in) or `OCIRegistryPuller` (`application/vnd.inari.template.v1` artifacts via `INARI_SCAFFOLD_TEMPLATE_OCI_INDEX_REF`, cosign keyless verification with `INARI_SCAFFOLD_TEMPLATE_VERIFY=true`). Manifests with `scaffold.requiresApproval: true` park runs in `pending_approval` after rendering (approvals.Gate + outbox ResumeHandler, same as orchestrator deploys); terminal runs are reaped after `INARI_SCAFFOLD_RUN_TTL`.
- Gateway = coarse PEP (valid JWT + org claim, route-level); services = fine PEP via OpenFGA `Check`/`ListObjects` behind an `Authorizer` interface (§5.4).
- Never store tenant kubeconfigs or cloud keys — only role ARNs, external IDs, OIDC metadata (§4.1, §5.10).
- Audit + events via the **outbox pattern** (append-only audit_events; outbox → NATS drives the OpenFGA tuple writer) (§5.2, §5.4).
- RBAC mapping materialization (plan §7.1, `internal/rbacmaterialize`): an outbox consumer (`tenant.created`, `team.created/deleted`, `rbac.mappings.updated`) re-renders the tenant's four anchor ClusterRoles (`tenant-<slug>-admin/operator/editor/viewer` — names pinned to the RBAC matrix API contract) + one role-qualified ClusterRoleBinding per team mapping (`tenant-<slug>-<team>-<role>` — role-qualified because roleRef is immutable: a mapping flip must create a new object that ArgoCD prunes the stale one for, never an in-place update; Group subject = `/tenant-<slug>/<team>`, matching Keycloak's full-path group claim — change `GroupSubjectName` only) and commits them to `baseline/rbac/` in the `<slug>-inari-state` repo (seeding the ArgoCD root app when the repo was created outside the TZF flow); the tenant-local ArgoCD syncs them. The git backend is selected with `INARI_GIT_PROVIDER`: `fake` (default), `github`, or `local` (filesystem bare repos under `INARI_GIT_LOCAL_ROOT`, go-git based, used by e2e).
- Tenancy = Keycloak **Organizations** in one `inari` realm; tenant ID is stable `org:<id>`; teams = groups `tenant-<slug>/<team>` (§5.4). Tenant deletion (ADR-0006): `DELETE /api/v1/tenants/{org}` freezes the org (`organizations.status='deleting'`), opens a platform-admin lifecycle approval (`tenant.decommission`), and runs the resumable `tenancy.Deleter` state machine (`tenant_deletions`: revoke_clusters → archive_audit → fga_cleanup → delete_keycloak_org → delete_org_row); FGA tuples are retracted synchronously from a DB snapshot, audit rows are archived to `audit_archive` under a TX-scoped GUC (`audit.allow_delete`), and reconcilers (`OrgTeamSync` via `ListActiveTeams`) skip non-active orgs so half-deleted tenants cannot be resurrected.
- kubectl access (plan §7.2): tenant creation auto-provisions the per-tenant kubelogin client `org-<slug>-kubectl` (`tenancy.EnsureKubectlClient`, idempotent): public, standard + device flow, audience `kubernetes`, claim `groups` with full group paths (`/tenant-<slug>/<team>`, leading slash — the exact strings `rbacmaterialize` binds as Group subjects; contract pinned in plan §5.4). `GET /tenants/{org}/clusters/{id}/access-info` returns the secret-free kubeconfig inputs (issuer, client ID, audience, org) — never the API-server URL (pull-only). Live verification: `e2e/kubectl-access.sh` (docker-only, no kind needed).
- Extension-gateway tunnel (ADR-0008): extension backends authenticate with per-extension identity — a dedicated Keycloak service-account client `ext-<name>` (client_credentials only, audience `inari-extension-gateway`) provisioned at registration; the tunnel validates `Authorization: Bearer` JWTs and resolves `azp` → the extension row. Secrets are returned once (register/`POST .../extensions/{id}/identity/rotate`), never persisted; unregister disables the client. The interim shared `INARI_EXTENSION_GATEWAY_TOKEN` is gone — never reintroduce a shared credential here.
- Contracts (protobuf/OpenAPI) come from the `inari-api` repo — pin its versioned packages; never fork contract types (§6).
- REST route registration lives in exactly one place: `internal/restsurface.Register(api, deps)`, consumed by BOTH the live binary (`cmd/inari-server`) and the offline exporter (`cmd/export-openapi`, nil deps — constructors/registration never dereference services). Never register huma routes in `cmd/*/main.go` directly, and never omit a module from the registry to keep it out of the published spec: the supported deliberate-exclusion mechanism is huma `Hidden: true` on the Operation. `cmd/export-openapi` tests assert structural parity (identical method+path sets) between the exported spec and live wiring.

## Conventions
- Conventional Commits; SemVer releases; container images/artifacts cosign-signed.
- Release flow (release-please, PR-only mode):
  1. `fix:`/`feat:` merges to `main` → `.github/workflows/release-please.yml` opens/updates a Release PR (version bump + CHANGELOG.md). Nothing else happens — no tags, Releases, or publishes.
  2. A maintainer manually merges the Release PR (human gate). CI lint/test/image checks must pass on the PR.
  3. `.github/workflows/release.yml` detects the release merge, creates+pushes tag `vX.Y.Z`, creates the GitHub Release, and invokes the reusable publish pipeline (`.github/workflows/publish.yml`, `workflow_call`): GHCR image push (`ghcr.io/7k-inari/inari-server`), cosign keyless sign, SBOM + SLSA provenance. The tag is pushed with GITHUB_TOKEN, so publish must not rely on tag-push triggers. The same pipeline also publishes the huma-generated OpenAPI contract (`make export-openapi`) as a cosign-signed OCI artifact `ghcr.io/7k-inari/inari-server-openapi:<version>` — inari-ui consumes it to codegen its client types; never hand-edit that artifact's source output.
  4. Per-commit edge images on main pushes stay in `.github/workflows/edge.yaml`. That workflow also publishes an edge OpenAPI spec artifact (`ghcr.io/7k-inari/inari-server-openapi:edge` + immutable, cosign keyless-signed `:main-<shortsha>`) so inari-ui can sync its pinned contract between releases; versioned spec tags still come only from the release pipeline above.
- Helm chart `charts/inari-server`: independent release-please `simple` component (tags `inari-server-chart-vX.Y.Z`), published to `oci://ghcr.io/7k-inari/inari-server/charts` by `chart-release.yaml`. Never bump `version:` by hand; `appVersion` is auto-synced to the server release via the root component's `extra-files`. CI lints (`helm lint`, `ct lint`) and runs helm-unittest.
- Write tests for new behavior; keep changes minimal and focused.
- Canonical architecture & development plan: https://github.com/7K-Inari/inari-docs/blob/main/docs/architecture/inari-platform-plan.md (section references below point into it).

## Platform design principles (apply everywhere)
1. Tenant-aware to the core — every object carries a tenant ID; every API decision is tenant-scoped.
2. Zero tenant credentials on the hub — no tenant kubeconfigs or cloud keys in the control plane.
3. Pull, never push — agents dial out; the control plane never initiates connections into tenant networks.
4. Desired state, eventually reconciled — GitOps/CR-based mutations, not imperative RPCs.
5. The catalog is a projection of reality — capabilities are discovered, not declared.
6. Small kernel, everything else extension.
7. Modular monolith first — strict internal module boundaries.
